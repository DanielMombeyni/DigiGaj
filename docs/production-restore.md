# انتقال بکاپ production به سرور جدید

دامنه این نسخه `digigadg.ir` است. این فرمان برای **مقصد تازه** طراحی شده و دیتابیس/والیوم موجود را پاک یا بازنویسی نمی‌کند. آن را روی سرور قبلی اجرا نکنید.

IP مبدأ جدید: **`87.107.54.205`**. Compose و فرمان restore مقدار `PUBLIC_SERVER_IP` را برای همین IP تنظیم می‌کنند؛ backend آن را پیش از تشخیص IP از سرویس‌های خارجی استفاده کرده و به allowed hosts اضافه می‌کند. URLهای اصلی و sitemap همچنان روی دامنه `.ir` می‌مانند. این متغیر در مهاجرت بعدی قابل تغییر است.

برای فرستادن بکاپ از PowerShell لپ‌تاپ به مقصد جدید، با جایگزینی نام واقعی فایل و پورت/نام کاربری SSH:

```powershell
scp -P 22 "$HOME\Downloads\DigiGajBackup\digigaj-backup.ABC12345.tar.gz" root@87.107.54.205:/root/
```

## پیش‌نیازها

- کد همین برنچ روی سرور جدید، Docker با Compose v2 دارای `up --wait`، و Python 3.10+ روی میزبان.
- برای HTTPS، OpenSSL و یک گواهی منقضی‌نشده با کلید منطبق که نام `digigadg.ir` را پوشش بدهد. گواهی `.com` کافی نیست.
- فضای کافی برای آرشیو اصلی، بازکردن آرشیو در پوشه موقت، build ایمیج‌ها و والیوم دیتابیس و تصاویر.
- بکاپ تهیه‌شده طبق روند این گفتگو: `database.dump` با فرمت custom مربوط به `pg_dump -Fc`، `media.tar.gz` از ریشه `/app/media` و `config.tar.gz` شامل `.env` و تنظیمات/SSL. بکاپ SQL متنی و کپی خام volume PostgreSQL پذیرفته نمی‌شوند.
- صحت SHA256 فایل انتقال را با فایل همراه `.sha256` بررسی کنید. اسکریپت ساختار و فایل‌های آرشیو و فهرست dump را بررسی می‌کند؛ امضای رمزنگاری یا اصالت منبع بکاپ را اثبات نمی‌کند.

## اجرا روی سرور جدید

برای HTTPS، گواهی جدید را در این مسیرها قرار دهید:

```text
deploy/ssl/ssl-certificate.pem
deploy/ssl/ssl-private.key
```

گواهی محلی معتبر اولویت دارد؛ در نبود آن، گواهی داخل بکاپ فقط در صورت اعتبار برای دامنه جدید انتخاب می‌شود. اعتبار نام، تاریخ و انطباق کلید بررسی می‌شود، اما اعتماد زنجیره عمومی گواهی و تنظیمات Cloudflare باید جداگانه بررسی شود. گواهی Cloudflare Origin برای اتصال مستقیم مرورگر معمولاً قابل اعتماد عمومی نیست.

داخل پوشه پروژه:

```bash
bash docker.sh Production restore /root/digigaj-backup.ABC12345.tar.gz
```

به جای آرشیو انتقال، پوشه‌ای که سه فایل در آن قرار دارند نیز پذیرفته می‌شود:

```bash
bash docker.sh Production restore /root/digigaj-backup.ABC12345
```

یا مسیر سه فایل، به این ترتیب:

```bash
bash docker.sh Production restore \
  /root/backups/database.dump \
  /root/backups/media.tar.gz \
  /root/backups/config.tar.gz
```

اگر عمداً فعلاً HTTPS نمی‌خواهید:

```bash
bash docker.sh Production restore /root/digigaj-backup.ABC12345.tar.gz --http-only
```

این حالت URLهای production را با `http://digigadg.ir` تنظیم می‌کند و با `DISABLE_ORIGIN_TLS=1` از فعال‌شدن تصادفی گواهی قدیمی در nginx جلوگیری می‌کند. برای فعال‌کردن HTTPS پس از آن، گواهی مناسب نصب کنید، در `.env` مقادیر `PUBLIC_SCHEME=https`، `TLS_ENABLED=true`، `DISABLE_ORIGIN_TLS=0` و URLهای عمومی/CORS/CSRF را روی HTTPS تنظیم کنید و سرویس‌ها را recreate کنید.

## مراحل خودکار

1. آرشیو را در پوشه موقت خصوصی باز می‌کند. مسیرهای مطلق، traversal، لینک‌ها، فایل‌های ویژه و ورودی‌های تکراری را رد می‌کند.
2. فرمت dump، ساختار آرشیو تصاویر و وجود `.env` اصلی را بررسی می‌کند.
3. تنظیمات محرمانه قبلی، از جمله `DJANGO_SECRET_KEY` و رمز دیتابیس، را حفظ و تنظیمات میزبانی را برای `.ir` و شبکه داخلی Docker بازنویسی می‌کند. `.env` با فرمت معمول تک‌خطی dotenv پشتیبانی می‌شود؛ آن را مثل اسکریپت shell اجرا نمی‌کند.
4. Compose config مؤثر را بدون چاپ رمزها بررسی می‌کند. وجود هر کانتینر همان پروژه یا هر والیوم مقصد، حتی خالی، باعث توقف می‌شود. اختلاف اطلاعات اتصال backend و db و فعال‌بودن seed نیز رد می‌شود. اگر این preflight رد شود، محتوای `.env` قبلی بازگردانده می‌شود.
5. ایمیج‌ها را می‌سازد و فقط PostgreSQL و Redis را بالا می‌آورد.
6. dump را با `pg_restore --single-transaction --exit-on-error` در دیتابیس تازه بازیابی می‌کند؛ `--clean` اجرا نمی‌کند.
7. تصاویر را داخل والیوم `media_prod` می‌ریزد؛ مالکیت و مجوزهای آرشیو را تحمیل نمی‌کند.
8. migration و collectstatic و Django check را اجرا و رکورد Django Sites را برای دامنه جدید تنظیم می‌کند. seed/bootstrap اجرا نمی‌شود؛ `SKIP_SEED=1` و `RUN_SEED=0` در محیط مقصد باقی می‌مانند.
9. backend، frontend و proxy را راه‌اندازی می‌کند. **Celery و beat به‌صورت پیش‌فرض خاموش می‌مانند.**

فایل قدیمی `docker-compose.prod.yml` یا اسکریپت/nginx قدیمی از آرشیو config روی کد جدید کپی نمی‌شود. `backend/.env` اختیاری حفظ می‌شود؛ فایل‌های SSL منتخب در مسیرهای استاندارد نصب می‌شوند.

پوشه خصوصی `.restore-state/` شامل نسخه قبلی فایل‌های تنظیمات تغییریافته و رسید تکمیل است و در Git نادیده گرفته می‌شود. این پوشه می‌تواند حاوی رمزها/کلید خصوصی باشد. قفل `restore.lock` از دو بازیابی هم‌زمان جلوگیری می‌کند؛ بعد از قطع اجباری فرایند، پیش از حذف قفل مطمئن شوید بازیابی دیگری اجرا نمی‌شود.

## بعد از بازیابی

```bash
bash docker.sh Production ps
bash docker.sh Production logs backend proxy
```

موفقیت فرمان یعنی مراحل محلی بدون خطای فرمانی تمام شده و Compose سرویس‌ها را running/healthy دیده است؛ سرویس‌های بدون healthcheck با `--wait` الزاماً از نظر HTTP آماده نیستند. **DNS یا HTTPS عمومی تأیید یا تغییر داده نمی‌شود.**

- رکورد A دامنه `digigadg.ir` را روی `87.107.54.205` تنظیم کنید؛ برای `www` از CNAME به دامنه اصلی یا A همین IP استفاده کنید. اگر AAAA قبلی دارید، آن را متناسب با IPv6 واقعی مقصد اصلاح/حذف کنید. حالت SSL مناسب Cloudflare را بررسی کنید. هیچ تغییر DNS از داخل این اسکریپت انجام نمی‌شود.
- صفحات، ورود کاربران، سفارش‌ها، شمارش محصولات، تصاویر و HTML خام `/sitemap.xml` را بررسی کنید.
- آدرس‌های مجاز Google OAuth، callback درگاه‌ها، وب‌هوک‌ها و لینک‌های خارجی را در سرویس‌های مربوط برای `.ir` تغییر دهید. محتوا/لینک دلخواه ذخیره‌شده در دیتابیس به‌صورت کورکورانه جایگزین نمی‌شود.
- پس از cutover و خاموش‌کردن workerهای سرور قدیمی، workerهای جدید را فعال کنید:

```bash
bash docker.sh Production up celery celery-beat
```

اگر می‌خواهید این فعال‌سازی نیز در انتهای فرمان بازیابی انجام شود، گزینه `--start-workers` را صریح اضافه کنید. این گزینه می‌تواند باعث اجرای کارهای زمان‌بندی‌شده یا ارسال اعلان شود.

Redis قدیمی در این بکاپ نیست. cache، OTPها، نتیجه taskها و صف pending منتقل نمی‌شوند. پیش از بکاپ نهایی، ثبت سفارش/تغییرات را در سرور قدیمی متوقف و صف‌ها را تخلیه/بررسی کنید؛ این فرمان مهاجرت آنلاین بدون وقفه یا همگام‌سازی سفارش‌های بعد از بکاپ نیست.

## در صورت شکست

خطا باعث توقف مراحل بعدی می‌شود. اسکریپت **هیچ volume یا داده‌ای را خودکار حذف نمی‌کند** و rollback کامل پس از شروع بازیابی ندارد. داده و تنظیمات نیمه‌بازیابی‌شده برای بررسی باقی می‌مانند؛ دوباره‌اجراکردن روی همان volumeها رد می‌شود. خطا را بررسی کنید و یک مقصد تازه انتخاب کنید یا بازیابی دستی همان مقصد را با آگاهی ادامه دهید. از `prune` یا `down -v` برای رفع خودکار خطا استفاده نکنید.

## اعتبارسنجی توسعه

```powershell
python -B -m unittest discover -s deploy/tests -v
```

تست‌های بک‌اند از پوشه `backend`:

```powershell
.\.venv\Scripts\python.exe -B -m pytest app/tests/test_site_domain.py app/tests/test_product_crawler.py app/tests/test_product_card_specs.py -m "not django_db" -v -p no:cacheprovider
```

نتیجه محلی این تغییر: ۱۴ تست میزبان، ۳۰ تست بک‌اند، Ruff، بررسی syntax سه اسکریپت shell، بررسی غیرفعال‌شدن seed و چهار بررسی فرانت‌اند موفق بودند. دو تست قبلی وابسته به دیتابیس عمداً انتخاب نشدند. ساخت فرانت‌اند در حافظه انجام شد و فایل خروجی تولید نکرد.

این تست‌ها Docker را mock می‌کنند و هیچ اتصال دیتابیس یا بازیابی واقعی ندارند. آزمون اختیاری OpenSSL، گواهی محلی موقت ایجاد می‌کند تا نام اشتباه `.com`، نام درست `.ir` و کلید نامعتبر را بررسی کند. تست‌های Django دستور دامنه نیز با دیتابیس مسدود اجرا می‌شوند. روی میزبان توسعه Docker در دسترس نبود؛ بازیابی کامل روی PostgreSQL/والیوم واقعی و دسترسی عمومی باید روی مقصد آزمایشی تازه جداگانه تأیید شود.

مراجع رفتار Compose: [run --no-deps](https://docs.docker.com/reference/cli/docker/compose/run/)، [up --wait](https://docs.docker.com/reference/cli/docker/compose/up/).
