# چک‌لیست استقرار سرور دیجی‌گج

استفاده: هر مورد را فقط وقتی تیک بزنید که **خودتان یا مالک/مدیر آن را تأیید کرده** باشید. موارد تأییدنشده را کامل‌شده علامت نزنید.

سندهای مرتبط:

- [راهنمای مبتدی](./server-deployment-guide.md)
- [محدودیت‌های شناخته‌شده](./server-deployment-known-limitations.md)
- [مرجع فنی production.md](./production.md)

---

## قبل از استقرار

- [ ] مالک پروژه URL مخزن Git را نوشته و تأیید کرده است (حدس نزده‌ام)
- [ ] شاخه و hash/`revision` تأییدشده برای استقرار مشخص است
- [ ] مالک تأیید کرده که این revision شامل همه migrationهای لازم (از جمله در صورت نیاز `0025`–`0028`) به‌صورت **commit‌شده** است
- [ ] استقرار از working tree کثیف انجام نمی‌شود
- [ ] IP/hostname سرور و حساب SSH از مدیر سرور گرفته شده است
- [ ] ورود SSH یک‌بار با موفقیت انجام شده است
- [ ] سیستم‌عامل سرور و دسترسی اجرای Docker تأیید شده است
- [ ] `docker version` و `docker compose version` روی سرور موفق است
- [ ] فضای دیسک کافی است (پیشنهاد مخزن: حداقل حدود ۲۰ GB؛ مقدار واقعی را مدیر تأیید کند)
- [ ] پورت‌های ۸۰ و ۴۴۳ (و SSH) از نظر فایروال/امنیت شبکه باز یا هماهنگ شده‌اند
- [ ] دامنه نهایی و مسئول DNS مشخص است
- [ ] مالک اجازهٔ کتبی/صریح استقرار Production داده است
- [ ] مقصد پشتیبان و اینکه چه کسی restore را بلد است مشخص است
- [ ] محدودیت‌های باز در [known-limitations](./server-deployment-known-limitations.md) خوانده شده‌اند

---

## پیکربندی محیط و اسرار

- [ ] فایل `.env` در ریشهٔ پروژه ساخته شده است
- [ ] `DJANGO_SECRET_KEY` دیگر مقدار نمونه نیست (مقدار واقعی را مالک داده)
- [ ] `POSTGRES_PASSWORD` قوی و غیر از مقدار نمونه است
- [ ] در صورت نیاز: `SIGNAL_SMS_*` توسط مالک پر شده یا صریحاً «فعلاً خالی» تأیید شده
- [ ] در صورت نیاز: Google OAuth / Telegram توسط مالک تعیین تکلیف شده
- [ ] هیچ فایل `.env` یا کلید خصوصی در چت عمومی / commit عمومی قرار نگرفته است
- [ ] ترتیب بارگذاری `.env` / `backend/.env` / `deploy.env` را از راهنما خوانده‌ام

---

## دامنه و TLS

- [ ] رکورد DNS به IP سرور (طبق گفتهٔ مالک/مدیر) تنظیم شده یا زمان‌بندی شده است
- [ ] اگر HTTPS لازم است: فایل‌های `deploy/ssl/ssl-certificate.pem` و `ssl-private.key` با PEM واقعی (نه فقط کامنت) آماده هستند
- [ ] فایل‌های گواهی commit نمی‌شوند
- [ ] اگر گواهی هنوز نیست: مالک صریحاً اجازهٔ موقت فقط-HTTP داده یا استقرار HTTPS را به تعویق انداخته است

---

## اولین استقرار

- [ ] در پوشهٔ `[PROJECT ROOT]` هستم (`docker.sh` و `docker-compose.prod.yml` دیده می‌شوند)
- [ ] از `./docker.sh` با محیط `Production` استفاده می‌کنم (روی سرور لینوکس)، نه قاطی کردن با `dev`
- [ ] تفاوت‌های `docker.ps1` را خوانده‌ام و تصادفی `prod`/`Production` را عوض نمی‌کنم بدون دانستن تفاوت
- [ ] می‌دانم `up` باعث build/start و **migrate خودکار** و seed شرطی می‌شود
- [ ] پشتیبان (اگر DB قبلی وجود دارد) گرفته و اندازهٔ فایل را چک کرده‌ام
- [ ] دستور اجرا شده: `./docker.sh Production up` (یا مسیر تأییدشدهٔ معادل)
- [ ] `./docker.sh Production ps` را دیده‌ام و سرویس‌های اصلی Up هستند
- [ ] لاگ `backend` و `proxy` را برای خطای واضح بررسی کرده‌ام
- [ ] صفحهٔ اصلی و مسیر API را با دامنه یا IP تأییدشده امتحان کرده‌ام
- [ ] ورود پنل/ادمین با اطلاعات مالک انجام شده و **رمز اولیه عوض شده** است

---

## قبل از هر به‌روزرسانی

- [ ] revision جدید از مالک تأیید شده است
- [ ] `git fetch` / checkout فقط همان revision تأییدشده
- [ ] تفاوت‌های مهم (به‌ویژه migrationهای جدید) با مالک مرور شده است
- [ ] پشتیبان تازه از دیتابیس گرفته و اندازهٔ فایل غیرصفر است
- [ ] در صورت وجود media مهم: پشتیبان media گرفته شده است
- [ ] زمان downtime کوتاه با مالک هماهنگ شده است
- [ ] دستور به‌روزرسانی تأییدشده (معمولاً `./docker.sh Production rebuild`) مشخص است — نه `prune`

---

## قبل از migration

- [ ] مالک صریحاً اجرای migration را تأیید کرده است
- [ ] زنجیرهٔ مورد انتظار (مثلاً تا `0028` در صورت شمول) با revision هم‌خوان است
- [ ] پشتیبان تأییدشده موجود است
- [ ] می‌دانم برگشت کد، migration را برنمی‌گرداند
- [ ] محیط هدف Production است نه `dev` و نه sms-test
- [ ] روش اجرا مشخص است: entrypoint هنگام up/restart یا `./docker.sh Production migrate`
- [ ] شخص ناظر برای شکست migration مشخص است

---

## بعد از استقرار / به‌روزرسانی

- [ ] `./docker.sh Production ps` بدون سرویس CrashLoop آشکار است
- [ ] فروشگاه (`/`) پاسخ می‌دهد (کد خطای ۵۰۲ نیست)
- [ ] `/api/v1/` در دسترس است یا خطای قابل توضیح دارد (نه ۵۰۲ مداوم)
- [ ] `/panel-dashboard` باز می‌شود
- [ ] در صورت انتظار HTTPS: سایت با https و بدون هشدار گواهی بحرانی (طبق دامنه واقعی) بررسی شده
- [ ] لاگ celery / celery-beat خطای تکرارشوندهٔ بحرانی ندارد
- [ ] آپلود/نمایش media در صورت نیاز کسب‌وکار یک‌بار دودویی چک شده
- [ ] SMS و پرداخت فقط اگر مالک خواسته دودویی (بدون تست مخرب) بررسی شده‌اند

---

## تمرین پشتیبان و بازیابی

- [ ] یک‌بار `pg_dump` طبق راهنما روی محیط مجاز اجرا و فایل ذخیره شده است
- [ ] محل نگهداری backup (دیسک سرور / خارج سرور) توسط مدیر تأیید شده است
- [ ] تمرین restore فقط روی محیط غیرضروری یا با تأیید کتبی مالک انجام می‌شود — روی Production زنده بدون تأیید نه
- [ ] پشتیبان media حداقل یک‌بار امتحان شده است
- [ ] تاریخ انقضای backupهای قدیمی و مسئولیت حذف ایمن مشخص است

---

## بازبینی امنیتی

- [ ] `DJANGO_SECRET_KEY` یکتا است
- [ ] `POSTGRES_PASSWORD` قوی است
- [ ] رمز کاربر bootstrap عوض شده است
- [ ] گواهی و کلید خصوصی در git نیستند
- [ ] فایروال: فقط پورت‌های لازم باز است (مدیر تأیید کند)
- [ ] دسترسی SSH محدود به افراد مجاز است
- [ ] دستورات `prune` / `down -v` به‌عنوان عیب‌یابی روزمره استفاده نمی‌شوند
- [ ] اسرار در مستندات یا تیکت عمومی paste نشده‌اند

---

## بازیابی اضطراری

- [ ] شماره/راه ارتباط مالک و مدیر سرور دم دست است
- [ ] آخرین backup سالم قبل از حادثه شناسایی شده است
- [ ] قبل از هر restore: وضعیت فعلی (در صورت امکان) دوباره backup شده است
- [ ] `prune` اجرا نمی‌شود مگر مالک صریحاً حذف کامل volume را بخواهد
- [ ] بعد از بازیابی: چک‌لیست «بعد از استقرار» دوباره طی می‌شود
- [ ] علت ریشه بعداً ثبت می‌شود تا تکرار نشود

## یادآوری محیط‌ها

| محیط | Compose | اسکریپت پیشنهادی |
|------|---------|------------------|
| توسعه | `docker-compose.dev.yml` | `./docker.sh dev …` |
| Production | `docker-compose.prod.yml` | `./docker.sh Production …` |
| Postgres تست SMS | `docker-compose.sms-test.yml` | جدا — **نه برای استقرار سایت** |

قبل از هر دستور، یک‌بار نام محیط را بلند بخوانید.
