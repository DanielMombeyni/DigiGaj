## جدول محدودیت‌ها

### 1. Isolation runtime دیتابیس تست SMS اثبات نشده

| | |
|--|--|
| **وضعیت** | `RUNTIME ISOLATION NOT PROVEN` |
| **چرا مهم است** | بدون شواهد runtime، هیچ‌کس نباید فرض کند تست‌های DB به دیتابیس Production/Dev نمی‌خورند. اتصال اشتباه می‌تواند داده را عوض کند. |
| **چه کسی حل کند** | توسعه‌دهنده / اپراتور با Docker در دسترس + مالک تأیید چک‌لیست |
| **شواهد لازم برای Resolved** | اجرای موفق stack `docker-compose.sms-test.yml`، تأیید پورت `127.0.0.1:55432`، volume نام‌دار `digigaj_sms_pytest_pgdata`، و ثبت چک‌لیست طبق `sms-test-isolation.md` — بدون اتصال به DB اپ |
| **مسدودکننده؟** | استقرار اولیهٔ **سایت** را مسدود نمی‌کند. تست‌های DBدار و ادعای «ایزوله‌بودن» را مسدود می‌کند. |

### 2. فایل‌های migration `0025`–`0028` ممکن است untracked باشند

| | |
|--|--|
| **وضعیت** | در زمان ممیزی روی working tree: untracked؛ روی `HEAD` commit‌شده نیستند مگر بعداً commit شوند |
| **زنجیره** | `0024` → `0025` → `0026` → `0027` → `0028` (`0028` به `0027` وابسته است) |
| **چرا مهم است** | `git clone` تمیز این فایل‌ها را ندارد. استقرار از dirty tree توصیه نمی‌شود. ورود ناقص زنجیره باعث شکست migrate می‌شود. |
| **چه کسی حل کند** | مالک پروژه / توسعه‌دهنده (commit + تأیید revision استقرار) |
| **شواهد Resolved** | `git ls-files` نشان دهد فایل‌ها trackedاند؛ revision استقرار آن‌ها را شامل شود |
| **مسدودکننده؟** | **بله برای استقرار ویژگی‌های وابسته به این migrationها.** برای استقرار revision قدیمی‌تر بدون آن ویژگی‌ها، فقط اگر مالک همان revision را تأیید کند. |

### 3. URL مخزن و revision تأییدشدهٔ استقرار

| | |
|--|--|
| **وضعیت** | در docs مقدار واقعی نیست (`<repository-url>`) |
| **چرا مهم است** | مبتدی نباید URL یا branch را حدس بزند |
| **چه کسی حل کند** | مالک پروژه |
| **شواهد Resolved** | URL و branch/hash به‌صورت مکتوب به اپراتور داده شده |
| **مسدودکننده؟** | **بله — قبل از clone/استقرار** |

### 4. IP سرور، SSH، DNS، وضعیت TLS واقعی

| | |
|--|--|
| **وضعیت** | خارج از مخزن؛ در ممیزی به Production وصل نشدیم |
| **چرا مهم است** | بدون دسترسی و دامنه، `up` روی سرور هدف ممکن نیست یا نیمه‌کاره است |
| **چه کسی حل کند** | مدیر سرور + مالک (دامنه/گواهی) |
| **شواهد Resolved** | SSH موفق؛ DNS تأییدشده؛ در صورت نیاز PEM واقعی روی `deploy/ssl/` |
| **مسدودکننده؟** | **بله برای استقرار کامل Production** |

### 5. Staging رسمی تعریف نشده

| | |
|--|--|
| **وضعیت** | فقط `dev` و `Production`/`prod` در اسکریپت‌ها؛ Staging جدا در compose نیست |
| **چرا مهم است** | خطر آزمایش مستقیم روی Production یا قاطی کردن با dev |
| **چه کسی حل کند** | مالک (تصمیم محصول) / در صورت نیاز توسعه‌دهنده (افزودن env) |
| **شواهد Resolved** | سند و compose جدا با نام پروژهٔ صریح، یا تصمیم مکتوب «Staging نداریم» |
| **مسدودکننده؟** | استقرار اول را لازم نیست مسدود کند؛ برای فرآیند امن به‌روزرسانی محدودیت عملیاتی است |

### 6. تفاوت رفتار `docker.sh` و `docker.ps1`

| | |
|--|--|
| **وضعیت** | تأییدشده در کد |
| **تفاوت‌ها** | نام env (`Production` در برابر `prod`)؛ `up` با/بدون `--build`؛ `seed` متفاوت؛ URLهای گمراه‌کننده در خروجی ps1 برای prod؛ نبود `seed-demo` در ps1 |
| **چرا مهم است** | اپراتور ممکن است فکر کند دو اسکریپت یکسان‌اند |
| **چه کسی حل کند** | ترجیحاً توسعه‌دهنده (هم‌ترازسازی بعدی)؛ تا آن زمان اپراتور از راهنما پیروی کند |
| **شواهد Resolved** | رفتار یکسان مستند و در کد، یا هشدار دائمی در usage اسکریپت‌ها |
| **مسدودکننده؟** | نه، اگر روی سرور لینوکس از `docker.sh` استفاده شود |

### 7. نام پروژهٔ Compose برای dev/prod ضمنی است

| | |
|--|--|
| **وضعیت** | `docker-compose.dev.yml` و `docker-compose.prod.yml` فیلد `name:` ندارند؛ پیش‌فرض معمولاً نام پوشه است. sms-test صریحاً `name: digigaj-sms-test` دارد |
| **چرا مهم است** | اجرای همزمان dev و prod از یک پوشه می‌تواند روی نام سرویس/پروژه تداخل بسازد؛ volumeها نام جدا دارند (`postgres_data_dev` / `postgres_data_prod`) ولی جداسازی پروژه صریح نیست |
| **چه کسی حل کند** | توسعه‌دهنده (افزودن `name:`) یا انضباط عملیاتی (checkout/مسیر جدا) |
| **شواهد Resolved** | `name:` صریح در هر دو فایل یا رویهٔ مکتوب مسیر جدا |
| **مسدودکننده؟** | برای یک سرور فقط-Production معمولاً نه؛ برای ماشین مشترک dev+prod **ریسک عملیاتی** |

### 8. تمدید خودکار TLS، rollback کامل، چرخش secret ناقص است

| | |
|--|--|
| **وضعیت** | نصب دستی Origin در `deploy/ssl/README.md` هست؛ runbook تمدید خودکار، rollback نسخه+DB، و rotation secret گام‌به‌گام کامل در مخزن دیده نشد |
| **چرا مهم است** | بعد از استقرار اول، عملیات روزمره مبهم می‌ماند |
| **چه کسی حل کند** | مالک + مدیر سرور (+ در صورت نیاز توسعه‌دهنده) |
| **شواهد Resolved** | سند رویه با تاریخ تست موفق روی سرور غیرمخرب یا Staging |
| **مسدودکننده؟** | استقرار اول را الزاماً نه؛ پایداری بلندمدت را محدود می‌کند |

### 9. وضعیت migration روی سرور موجود ناشناخته است

| | |
|--|--|
| **وضعیت** | ممیزی به DB زنده وصل نشد |
| **چرا مهم است** | بدون دانستن برگ فعلی، `migrate` ممکن است مجموعهٔ بزرگی اعمال کند یا خطا بدهد |
| **چه کسی حل کند** | مدیر سرور / اپراتور با اجازهٔ مالک (`showmigrations` روی محیط درست) |
| **شواهد Resolved** | خروجی `showmigrations` ذخیره‌شده قبل از تغییر |
| **مسدودکننده؟** | **بله قبل از migrate روی سروری که از قبل DB دارد** |

### 10. این مستندات جایگزین تست Production نیستند

| | |
|--|--|
| **وضعیت** | راهنما statically از روی کد نوشته شده؛ سرور واقعی در فاز مستندسازی تست نشده |
| **چرا مهم است** | «داشتن راهنما» ≠ «سایت روی سرور آماده است» |
| **چه کسی حل کند** | اپراتور پس از طی دروازه‌ها + تأیید مالک |
| **شواهد Resolved** | چک‌لیست بعد از استقرار روی سرور واقعی تیک خورده |
| **مسدودکننده؟** | ادعای «آمادهٔ Production» را مسدود می‌کند تا شواهد بیاید |

## نحوهٔ علامت‌زدن Resolved

برای هر ردیف، در همین فایل یا تیکت داخلی اضافه کنید:

1. تاریخ  
2. نام تأییدکننده  
3. نوع شواهد (مثلاً خروجی فرمان غیرمحرمانه، شماره commit)  
4. لینک به راهنما/چک‌لیست به‌روز  

تا آن زمان، راهنمای مبتدی باید خواننده را به «توقف و پرسیدن» هدایت کند — نه حدس.
